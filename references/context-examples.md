# 문맥 판독 사례

tone-rules.md §12 기제의 문단 단위 사례. 대부분 1.3.0 스킬로 교정해 스크립트 단언 17개를 모두 통과한 eval-3 보고서에 남은 문장이다. 문장 하나만 보면 멀쩡하고 앞뒤 문단을 함께 읽어야 보이므로 문맥째 둔다.

사례의 표현을 외워 찾지 않는다. 같은 기제는 다른 문서에서 다른 단어로 나온다. 각 사례의 `왜` 에 적힌 판별 질문을 새 문서에 적용한다.

✅

> **Orca는 지원 에이전트 전부를 권한 우회 플래그로 미리 채워(pre-fill) 실행한다.**
>
> Claude는 `--dangerously-skip-permissions`, Codex는 `--dangerously-bypass-approvals-and-sandbox`, Gemini와 Cursor는 `--yolo`다. 근거로 "worktree는 일회용(disposable)"을 든다. 중간 권한 모드(Claude Auto, Codex "Approve for me")는 아직 선택 불가다(이슈 #13081).

## 사례 2: 세 문단 뒤에 리드를 다시 말하는 재진술 (§12.2)

❌

> **Orca 역할 간 계약의 3요소: 메시지 타입, 필수 ID, outcome**
>
> (중략: Run, Task, Dispatch 정의 목록)
>
> **워커 완료와 heartbeat 메시지는 `taskId`와 `dispatchId`를 모두 담는다.**
>
> 오래된 워커가 최신 작업을 완료 처리하는 것을 막기 위해서다. `worker_done`은 정확히 한 번, `--outcome succeeded|failed`와 함께 보낸다. 완료 권한(completion authority)은 활성 dispatch 컨텍스트에서 나온다.
>
> 이것이 supervisor/executor 역할 사이의 "메시지 타입 + 필수 ID + outcome" 계약이다. 역할 분리 원칙은 공식 사이트에 인용된 사용자 포스트가 압축한다.

✅

> (앞 두 문단 그대로)
>
> 역할 분리 원칙은 공식 사이트에 인용된 사용자 포스트에 있다.

왜: 절 리드가 이미 계약 3요소를 말했다. 재진술 시험에 걸린다. 낱말이 겹쳐 판독표 `재진술 후보` 에 나오지만, 낱말이 달라도 같은 말이면 같은 처리다. "포스트가 압축한다" 는 글을 주어로 세운 의인화(§8.11)다.

## 사례 3: 리드 전체를 받는 꼬리표 (§12.3)

❌

> **verdict는 severity level을 포함한 구조화된 JSON으로 산출한다.**
>
> Codex reviewer 패턴의 권장 형태다. 커뮤니티(sdlc.xeb.ai의 Playbook 정리)가 강조하는 원칙은 두 가지다.
>
> - test/feature manifest 는 append-only 로 둔다.
> - 모든 'done' 주장에 검증 artifact 를 첨부한다.

✅

> **Codex reviewer 패턴은 verdict 를 severity level 이 담긴 JSON 으로 내도록 권장한다.**
>
> 커뮤니티 정리(sdlc.xeb.ai 의 Playbook 정리)가 함께 강조하는 원칙
>
> - test/feature manifest 는 append-only 로 둔다.
> - 모든 'done' 주장에 검증 artifact 를 첨부한다.

왜: "Codex reviewer 패턴의 권장 형태다" 는 주어 없이 리드 전체를 받는다. 출처를 주어로 올리면 리드 한 문장이 된다. "원칙은 두 가지다" 는 §10.5 개수 예고라 명사구로 바꾼다.

## 사례 4: 리드 되풀이, 지시어 꼬리, 명사화가 한 문단에 (§12.2, §12.1, §12.4)

❌

> **모델 종속 조정 문구는 세 하네스 모두에서 시스템 프롬프트와 skill 파일에 흩어져 있다.**
>
> (a) 시스템 프롬프트/AGENTS.md/CLAUDE.md, (b) skill 파일이 그 자리다. 이것이 재작성 비용의 근원이며, 해결책은 단일 모델 어댑터 파일로의 격리다(5절).

✅

> **모델 종속 조정 문구는 세 하네스 모두에서 시스템 프롬프트와 skill 파일에 흩어져 있다.**
>
> 모델이 바뀔 때마다 이 문구를 전부 다시 쓴다. 문구를 어댑터 파일 하나로 옮기면 다시 쓸 곳도 그 파일 하나로 줄어든다(5절).

왜: 첫 문장은 리드를 되풀이한다. "이것이 ~의 근원이며" 는 지시어로 앞 내용을 받는 꼬리이고, "~로의 격리" 는 명사화다. 동작을 동사로 펴면 원인과 해결이 사실 문장 두 개로 남는다.

## 사례 5: 리드와 본문에 두 번 나오는 직역 숙어 (§12.5, §12.2)

❌

> **Orca 오케스트레이션의 유일한 진실 소스: `orca skills get orchestration --full`**
>
> 레거시 명령은 deprecated 되어 효과가 없다. 플래그는 앱 버전에 따라 바뀌므로 `orca skills get orchestration --full`이 유일한 진실 소스(source of truth)다.

✅

> **Orca 오케스트레이션 플래그의 최종 기준: `orca skills get orchestration --full`**
>
> 레거시 명령은 deprecated 되어 효과가 없다. 플래그가 앱 버전마다 바뀌므로 실행 전에 이 명령으로 확인한다.

왜: "진실 소스" 는 source of truth 를 역번역 시험에 걸면 바로 나온다. 리드에서 한 말을 본문 끝에서 다시 하므로 본문은 할 일로 바꾼다.

## 사례 7: 문서 안에서 스스로 반박되는 최상급 (§12.6)

✅

> 3단계 hook/gate 를 세운다. "task done 보고 전 검증 통과" 와 "수정 중 테스트 파일 편집 차단" 을 hook(exit code 2)으로 구현한다. Orca 가 권한 우회를 pre-fill 하므로 실제 차단은 이 gate 가 맡는다.

## 사례 8: 앞 절과 뒤 절이 어긋나는 논리 (§12.8, §12.4)

❌

> **두 migrate 스킬 모두 프롬프트 행동 튜닝과 eval 검증은 사람에게 남긴다.**
>
> 모델 문자열, 파라미터, effort 같은 기계적 변경은 자동화한다. 모델별 조정 문구는 자동 생성될 수 없는 판단 영역이고, 이를 모델 어댑터 파일 하나에 모으면 migrate 스킬이 그 파일을 재생성 대상으로 삼을 수 있다.

✅

> **두 migrate 스킬 모두 프롬프트 행동 튜닝과 eval 검증은 사람에게 남긴다.**
>
> 모델 문자열, 파라미터, effort 같은 기계적 변경만 자동화한다. 조정 문구는 migrate 스킬이 대신 써 주지 못한다. 문구를 어댑터 파일 하나에 모아 두면 사람이 고칠 곳이 그 파일로 줄어든다.

왜: 앞 절은 자동 생성할 수 없다고 하고 뒤 절은 재생성 대상이라고 한다. 원문(벤더 문서의 "manual verification ... prompt tuning")과 리드가 사람 몫이라고 하므로 그쪽에 맞춘다. 원문으로 확인할 수 없으면 고치지 말고 보고에 남긴다. "판단 영역" 은 명사화다.

✅

>

왜: 둘째 문장은 알람, 산식, 수치를 지워도 아무 문서에나 붙는다. 한계를 말해야 하면 이 산식의 실제 한계(남은 오탐 2건의 원인)를 원문에 있는 사실로 쓴다.

## 사례 10: 단어만 피한 1차 교정 (§12.14, §12.1, §12.5)

❌ (원문 "증거가 실무·연구 양쪽에서 수렴한다" 를 고친 결과)

> **교차 모델 리뷰의 이점은 실무 보고와 연구 양쪽에서 확인된다.**
>
> 같은 모델이 코드를 쓰고 리뷰하면 상관된 맹점을 재생산한다. Augment Code는 Codex reviewer가 Claude 계열이 놓친 버그를 찾아 실제 CVE를 산출한 libfuse 캠페인을 보고했다(3절 인용).

✅

> **다른 계열 모델의 리뷰가 같은 모델의 자기 리뷰보다 버그를 더 많이 찾는다.**
>
> 같은 모델은 코드를 쓸 때 놓친 실수를 리뷰할 때도 놓친다. Augment Code 의 libfuse 캠페인에서는 Codex reviewer 가 Claude 계열 리뷰가 놓친 버그를 찾았고, 그 버그가 CVE 로 공개되었다(3절 인용).

왜: '수렴' 을 '양쪽에서 확인된다' 로 바꿔 단어만 피했다. 리드는 이점이 무엇인지 말하지 않고 근거가 있다는 사실만 말한다. "상관된 맹점을 재생산한다" 는 correlated blind spots 를 낱말대로 옮겼다. 고친 문장에도 판별 질문을 다시 던진다.

>
> **판단 전까지의 예산 집행에는 정량적 근거가 없다.**

> 현행 판단 흐름은 다음과 같다.
>
> 1. (판단 절차 3단계)
>
> 단순하고 오래 검증된 기준이지만, 다음 네 가지 한계가 있다.
>
> ### 2.1 …

왜: "다음 네 가지 한계가 있다" 는 개수만 말하는 틀이 아니다. '단순하고 검증됐다' 는 인정과 '한계가 네 가지' 라는 판정을 양보 관계로 함께 싣고, 긴 절의 소절 네 개를 예고한다. ❌ 판은 이 문장을 콜론 목록으로 바꿔 아래 소제목 네 개를 미리 되풀이했고, 인정 문장은 절차 목록 앞으로 옮겨 양보 관계를 끊었다.

## 사례 14: 조어, 어울리지 않는 서술어, 구어가 한 절에 (§12.12, §12.11, §12.10)

❌

> ### 2.2 단일 배수가 놓치는 매체별 곡선 차이
>
> **같은 D30 ROAS 35%라도 D90은 매체 B 71.8%, 매체 C 56.7%로 갈린다.**
>
> 목표 70% 기준으로 매체 B는 통과, 매체 C는 미달이다. 타이틀 단위 배수(1.84배)로 계산하면 둘 다 64.4%로 같은 판단이 나온다.

✅

> ### 2.2 매체별 곡선 차이를 반영하지 못하는 타이틀 배수
>
> **같은 D30 ROAS 35%라도 D90 ROAS는 매체 B 71.8%, 매체 C 56.7%로 차이가 크다.**
>
> 목표 70% 기준으로 매체 B는 통과, 매체 C는 미달이다. 그런데 타이틀 단위 배수(1.84배)를 적용하면 둘 다 64.4%로 판단 기준이 같아진다.

왜: '단일 배수' 는 문서가 정의하지 않은 합성어라 무엇을 가리키는지 모호하다(1x 배수로도 읽힌다). '갈리다' 는 의견처럼 의지를 가진 주체 사이에 쓰고, '판단' 에 어울리는 동사는 '내리다' 다. '그런데' 는 통과, 미달이 같은 판단으로 뭉개지는 대조를 실제로 잇는다(§12.8).

## 사례 15: 구어를 문어로 (§12.10)

| ❌ 구어 | ✅ 문어 |
|---|---|
| 이들이 머릿속에 둔 D90/D7 배수는 2.5~4.0배로 제각각이었다. | 이들이 기준으로 삼은 D90/D7 배수는 2.5~4.0배로 제각각이었다. |
| 초반 점의 출렁임에 민감하다. | 초반 데이터의 변동에 민감하다. |
| 그래디언트 부스팅이 현행 D30과 2.2~2.4%p 차이까지 따라왔다. | 그래디언트 부스팅이 현행 D30에 2.2~2.4%p 차이로 근접했다. |
| UA팀이 숫자를 믿고 쓰려면 | UA팀이 예측치를 믿고 쓰려면 |
| 나머지 두 방식에서는 뚜렷한 편향이 보였다. | 나머지 두 방식에서는 뚜렷한 편향이 나타났다. |
| 대형 업데이트 전후 4주에 시작한 캠페인은 판단 보류로 돌린다. | 대형 업데이트 전후 4주에 시작한 캠페인은 판단 보류로 전환한다. |

왜: 말로는 자연스러워도 의사결정자에게 보내는 보고서의 격에 맞지 않는다. '원문 어휘를 존중한다' 는 이유로 남기지 않는다. 지켜야 할 것은 사실과 명제다.
