# Tone Rules — 어조 · 어법 · 구조 · 가독성 규칙

청중에 맞는 어조로 통일하는 룰. 의사결정자 대상이 기본값. 단계 매핑: §1~§8.16 = 1단계(패턴), 2a단계(문장·어휘), §10 = 2b단계(문단·구조), §9·§11 = 3단계(가독성).

---

## 1. 어법 — 명령·예측 ❌ vs 사실·계획 ✅

보고서 본문은 사실 + 계획 + 일정의 단정 형태. 명령형(`해야 합니다`) 또는 예측형(`지연됩니다`) 어법은 피한다.

| ❌ 금지 | ✅ 사용 |
|---|---|
| "해야 합니다" | "마무리 조건입니다" |
| "지연됩니다" | "도달 예정입니다" |
| "X 해주세요" | "X 가 5/29 마감입니다" |
| "주의가 필요합니다" | "기준점입니다" |

---

## 2. 1인칭 회피

작성자가 "저희" / "우리 측" / "우리는" 같은 1인칭을 쓰면 방어 톤이 침투한다. 사실 명사구 또는 시스템 명사로.

| ❌ 금지 | ✅ 사용 |
|---|---|
| "저희가 단축할 수 없는" | "시간 의존 구간" |
| "우리 측 작업" | "5월말 마감 작업" |
| "저희가 통제할 수 없는" | "외부 일정 의존" |
| "우리가 ~합니다" | 주어 생략 또는 "X 가 ~합니다" |

---

## 3. 명사화 정형 — 가정형 부정문 ❌ vs 단정 명사구 ✅

가정형 부정 시나리오(`만약 ~ 늦으면 ~ 지연됩니다`)는 보고서에 들어가지 않는다. 명사구로 단정.

| ❌ 금지 | ✅ 사용 |
|---|---|
| "X 가 늦으면 Y 가 늦어집니다" | "X 시점이 Y 도달일을 결정합니다" |
| "X 가 지연되면 Y 도 지연됩니다" | "X 는 Y 의 선행 조건입니다" |
| "X 가 슬립하면 Y 도 슬립됩니다" | "X 는 Y 의 기준점입니다" |
| "X 가 밀려도 진행은 가능합니다" | "X 는 Y 마감 조건의 일부입니다" |

---

## 4. 추측·가능성 단어 금지

"슬립 가능성", "예상", "지연될 수 있습니다" 같은 단어는 소스에 명시 인용일 때만 사용. 자동 삽입 금지.

| ❌ 금지 | ✅ 사용 |
|---|---|
| "슬립 가능성이 있습니다" | (소스 인용일 때만) |
| "지연될 수 있습니다" | "X 일정의 기준점입니다" |
| "예상 슬립" | (소스 어휘 인용일 때만) |
| "추정됩니다" | (소스 인용일 때만) |

소스에 명시 인용일 때도 따옴표로 묶거나 inferred 표식.

---

## 5. 친근·메타 표현

청중이 의사결정자일 때:

| ❌ 금지 | ✅ 사용 |
|---|---|
| "X 에게 —" | 호칭 자체를 본문에 쓰지 말 것 |
| "여러분께서" | 주어 생략 또는 시스템 명사 |
| "발신 / 수신 / 기준일 / 다음 보고" | (명시 요구 없으면 생략) |
| "친근한 한 마디" 식 도입 | verdict 로 바로 시작 |

---

## 6. 어미 — 존대어 통일

청중이 의사결정자일 때 본문은 존대어. 평어체와 혼용 금지.

| ❌ 평어 | ✅ 존대 |
|---|---|
| "마감이다" | "마감입니다" |
| "결정한다" | "결정합니다" |
| "기준점이다" | "기준점입니다" |
| "있다" | "있습니다" |

UI 라벨(예: 칩 라벨 `★ Basic 30일`)이나 표 셀(예: `완료`)은 존대 변환 안 함. 본문·설명문만 존대.

---

## 7. 주어 처리

주어를 명확히 두되, 1인칭 대신 시스템/구성요소 명사 사용.

| ❌ 1인칭 | ✅ 시스템 명사 |
|---|---|
| "우리는 5/29 까지 해결합니다" | "차주(5/29) 해결 예정입니다" |
| "저희가 SDK 를 5/31 에 릴리즈합니다" | "5/31 SDK 릴리즈 타겟입니다" |
| "우리는 파트너사와 계약 갱신을 합니다" | "파트너사 계약 갱신이 필요합니다" |

---

## 8. 제목·소제목 — AI 상투 제목 금지

제목이 "이제부터 설명하겠다"는 운만 떼면 AI스럽게 읽힌다. **명사구로 그 섹션의 결론/대상을 직접 명시**한다. 제목만 읽어도 내용·판정이 파악되어야 한다.

| ❌ AI스러운 제목 | ✅ 명사구 제목 |
|---|---|
| "한눈에 — 무엇으로 무엇을 예측하나" | "개요 — 코호트 피처로 장기 LTV 예측" |
| "설계 특징 — 왜 이렇게 나뉘어 있나" | "설계 특징 — 코호트·수익유형·관측기간 분리" |
| "데이터, 어떻게 봐야 할까" | "데이터 품질 점검 우선순위" |
| "왜 중요한가" | "중요성" / "신뢰의 근거" |
| "이게 무엇인가 / 어떤 구조인가" | 대상 명사구로 직접 ("3-테이블 구조") |
| "모델을 알아보자" | "예측모델 3-테이블 구조" |
| "이 덱의 구성 / 이 문서의 목적" | "구성" (또는 라벨 자체 생략) |
| "외부 플랫폼 연동 전 과정" (장황한 운떼기) | "연동 과정 소개" |
| "결정을 바꾸는 임계치 — 추가 결함 검출률·first-pass CI success rate·정책 리뷰 코멘트 수" (관형절 + 추상명사, 번역투) | "판단 기준: 결함 검출률, CI 통과율, 정책 리뷰 코멘트 수" / "방침을 바꿀 시점" |
| "행동을 유발하는 조건" / "성패를 가르는 지표" | "실행 조건" / "핵심 지표" |

금지 신호:
- **수사의문문·대화체**: `~하나 / ~할까 / ~인가 / ~한가 / ~는가 / ~ㄴ가 / 왜 ~인가 / ~있나 / ~없나 / 무엇을 ~ / 어떻게 ~`. 제목·부제·라벨이 **의문형 어미(`인가/한가/는가/ㄴ가/을까/나요`)로 끝나면** 무조건 명사구로 교체. (예: `왜 중요한가` → `중요성`, `무엇을 하는 플랫폼인가` → `플랫폼 정의`)
- **상투적 도입어**: `한눈에 / 살펴보기 / 알아보기 / 쉽게 말해 / 정리하면 / 자세히 보기 / ~란?`
- **막연한 추상어만**으로 된 제목 (내용을 안 드러냄)
- **자기지칭 메타 라벨**: `이 (덱·문서·장표·자료)의 (구성·목적·내용·개요)` → 명사 한 단어(`구성`)로 줄이거나 라벨 자체 생략
- **수사적 3연 나열**: `어떤 ~ 거치고, 무엇을 ~하며, 무엇을 ~하는가` → 대상을 명사구 리스트로 (`연동 6 스텝, 외부 연동 대상, 연동 후 데이터`)
- **관형절 + 추상명사 조합**: `결정을 바꾸는 임계치 / 행동을 유발하는 조건 / 성패를 가르는 지표` 는 영어 "decision-changing thresholds" 의 직역이다. 동료에게 소리 내어 말할 표현인지 본다. 아니면 `판단 기준`, `실행 조건` 같은 일상 명사로.

(실측 피드백: "결정을 바꾸는 임계치? 이런 문장 표현을 쓰나? 사람이 쓰는 표현으로 해줄래?")

형태 규칙: `대주제: 구체 명사구`. 콜론 뒤 부제도 **질문형이 아니라 명사구**로. (예: `알고리즘: k-NN 6단계` ✅ / `알고리즘: 어떻게 동작하나` ❌). 구분자로 대시는 쓰지 않는다(§8.6).

## 8.1 내용 없는 메타 문장 금지 (부제·리드·본문)

부제/리드가 "이 장이 무엇을 다루는지"를 **메타로 서술만 하고 실제 정보를 안 담으면** 삭제하거나 사실 문장으로 교체한다. AI 가 화면을 채우려고 넣는 가장 흔한 군더더기다.

| ❌ 빈 프레이밍 (정보 없음) | ✅ 사실 / 명사구 / 삭제 |
|---|---|
| "각 단계가 어디서 무슨 작업인지로 본다 — A 와 B 가 갈린다" | "다음 6 단계로 진행한다" (또는 삭제) |
| "이 과정을 통해 전체 그림을 이해한다" | (삭제) |
| "무엇을 연동하며 무엇을 보게 되는가" | "연동 대상 · 연동 후 데이터" |
| "~를 살펴본다 / ~인지로 본다 / ~를 알아본다" | 대상을 바로 명사구로 제시 |

**판별법**: 부제에서 고유명사·수치·구체 동작을 지워도 문장이 그대로 "성립"하면 빈 프레이밍이다 → 삭제 또는 사실로 교체. 메타 동사(`본다 / 살펴본다 / 알아본다 / 이해한다`)로 끝나는 부제는 의심.

**부제·리드는 명사절/명사구로 끝낸다 — 술부 문장(`~다 / ~한다 / ~된다`) 금지.** 덱 부제는 문장이 아니라 라벨이다. 술부를 떼고 핵심 명사로 닫는다.

| ❌ 술부 문장 부제 | ✅ 명사절 부제 |
|---|---|
| "게임에 외부 SDK를 붙이는 작업은 6 단계로 진행한다" | "게임에 외부 SDK를 붙이는 6 단계" |
| "…데이터를 수집한다. …의 원천이다" | "…데이터 — …의 원천" |
| "별개 시나리오 세 가지. 검증을 누가 하느냐가 다르다" | "검증 주체가 다른 별개 시나리오 세 가지" |

> 정보를 담은 한 줄이 없으면 **부제 자리를 비우는 편이 낫다**. 채우기용 문장은 넣지 않는다.

## 8.2 메타 노트 누출 · 중언부언 금지

**(1) 작성자용 메타 노트를 산출물에 남기지 않는다.** 검토자·작성자에게 설명하려고 괄호로 단 주석은 최종 문서에 들어가면 안 된다. 괄호 안 내용이 *독자가 아니라 나에게* 하는 말이면 삭제.

| ❌ 누출된 메타 노트 | ✅ |
|---|---|
| "인증 정보 (모듈별 유사)" | 라벨은 "입력 정보 예시", 다름은 별도 코멘트 "모듈마다 다름" |
| "캠페인 종류 (여기에 18종 나열)" | 실제로 나열하거나 "캠페인 18종" |
| "개요 (예시로 채움)" / "(작성자 확인)" / "(TODO)" | 메타 설명 제거 — 예시면 "예시"만 |

**(2) 중언부언·불필요 정보를 노출하지 않는다.** 앞에서 말한 것을 다시 말하거나(restate), 당연한 동작을 굳이 서술하지 않는다. 그 문장을 지워도 독자가 잃는 정보가 없으면 삭제.

| ❌ 중언부언/군더더기 | ✅ |
|---|---|
| "프로젝트 규모에 따라 다르며, 포인트마다 이 흐름을 반복한다" | "프로젝트 규모에 따라 다름" |
| "이를 통해 ~할 수 있다" / "~하면 된다" | (대개 삭제 — 정보 없음) |
| 절차를 나열한 뒤 "이 단계를 반복한다" 재서술 | 한 번만, 재서술 삭제 |
| 정의 표 뒤 "5절의 레이아웃과 체크리스트가 이 표의 단계 이름을 쓴다" / "이후 본문은 이 표의 이름으로 지칭한다" (문서 내부 참조 안내) | (삭제. 독자는 표를 보면 안다) |
| "자세한 내용은 아래 절에서 다룬다" / "위에서 정의한 대로" | (삭제. 필요하면 절 번호만 괄호로) |

**자명한 부연은 쓰지 않는다.** 위 표의 "이 표의 단계 이름을 쓴다" 는 한 문서에서 나온 예시일 뿐이고, 문서마다 다른 모습으로 나타난다. 공통점은 독자가 배치만 보고도 아는 사실(표 뒤 절이 표의 용어를 쓴다, 목록 다음에 상세가 온다, 정의한 용어를 이후에 쓴다)을 문장으로 설명한다는 것이다. 표, 절, 목록이 어떻게 이어지는지는 배치 자체가 보여 준다. **판별법**은 (2)와 같다: 그 문장을 지워도 독자가 잃는 정보가 없으면 삭제.

(실측 피드백: "5절의 디렉터리 레이아웃과 온보딩 체크리스트가 이 표의 단계 이름을 쓴다. 이런 부연 설명은 불필요하다. 명백하고 굳이 설명할 필요가 없는 내용이기 때문이다" / "이 문구는 이 문서 한정이다. 예시로 들어가야 한다. 다른 문서에서는 다른 표현을 쓸 거니까")

**(3) 빈 공간을 막연한 일반화로 채우지 않는다.** 다이어그램 여백·카드 옆·표 끝처럼 *남는 자리*를 메우려 두루뭉술한 문구를 넣지 말 것. 구체적·비자명한 정보가 없으면 **그냥 비운다.**

| ❌ 채우기용 막연 문구 | ✅ |
|---|---|
| (다이어그램 여백) "그 외 수집 SDK 도 직접 연결" | (삭제 — 여백으로 둠) |
| "기타 다양한 항목들 / 등등 여러 가지" | 구체 나열하거나 삭제 |
| "필요 시 상황에 맞게 처리" | (정보 없음 → 삭제) |

> 판별: 그 문구에서 고유명사·수치·구체 동작을 빼도 말이 그대로 성립하면(=아무 맥락에나 붙는 일반론) 채우기용이다 → 삭제.

> 핵심: **덱은 노출 면적이 작다.** 한 칸에 들어갈 정보만 남기고, 설명·반복·메타·채우기는 전부 버린다.

## 8.3 제목 수량 꼬리표 금지 · 비전문가 어휘 금지

**(1) 제목에 수량 꼬리표(`~N종 / ~N개 / ~가지`)를 붙이지 않는다.** 수는 부제로 옮긴다.

| ❌ 제목 | ✅ |
|---|---|
| "MMP 연동 모듈 2종" | 제목 "MMP 연동 모듈" + 부제 "Adjust·AppsFlyer 2종" |
| "리포트 12종" | 제목 "리포트와 대시보드" + 부제 "12종" |

**(2) 비전문가·구어체 동사·명사를 쓰지 않는다.** 실무 전문가 어휘로 쓴다.

| ❌ 구어/일상어 | ✅ 전문 |
|---|---|
| "데이터를 받는다 / 붙인다 / 켠다" | "수집한다 / 연동한다 / 활성화한다" |
| "캠페인을 띄운다" | "캠페인을 노출한다" |
| "유저를 다르게 대한다" | "유저별로 다르게 적용한다" |
| "한 판 길이 / 한 판" | "플레이 시간 / 세션" |
| "사내가 먼저 발굴한다" (사내 를 주어로 — 비문) | "먼저 찾아낸다" / "사내에서 발견한다"(부사어) |
| "문제점을 발굴한다" (발굴=땅을 파다, 어색) | "문제점을 찾아낸다 / 발견한다" |
| "갈아 끼운다 / 갈아 끼울 부분" | "교체한다 / 변경 범위" |

**(3) 내부 식별자(리포 이름·코드명)를 독자에게 노출하지 않는다.** 내부 리포지토리 코드명(예: `project-internal-xyz`) 같은 것 대신 사람이 읽는 이름·링크로.

**(4) 홍보 문구를 넣지 않는다.** 내부 공유 문서엔 `코드 배포 없이` 같은 셀링 카피를 쓰지 말 것 — 기능·현황·남은 작업만.

## 8.4 확인된 사실만 — 미확정 구체(방식·시점·메커니즘) 단정 금지

소스/사용자가 준 사실의 **범위를 넘어 그럴듯한 구체를 덧붙이지 않는다.** AI 는 "X 지원 개발 중"만 들으면 *어떻게*(내장? 플러그인?) ·*언제*(다음 분기?) 까지 자동으로 채워 단정하는 경향이 있다. 이건 §4(추측 *단어* 금지)의 반대 실패 — **확신형 과잉 구체화**이고, 사실상 날조다.

| ❌ 미확정 구체 단정 | ✅ 아는 범위만 |
|---|---|
| "**내장(embedded)** 미디에이터 지원 추가 작업 진행 중" (구현 방식 미확정) | "지원 개발 진행 중" |
| "곧 출시 / 다음 분기 지원" (시점 미확정) | "지원 예정" (시점 언급 없이) |
| "자동으로 처리된다 / 내부적으로 ~한다" (동작 미확인) | (확인 전이면 쓰지 않음) |
| "AppLovin 처럼 설치만으로 동작하도록" (방식 단정) | (방식 미정이면 비교·단정 모두 제거) |

> 판별: 그 구체(방식·시점·동작)가 **소스/사용자 발언에 실제로 있었나?** 없으면 빼고 "아는 사실"까지만 적는다. "있을 법해서" 채운 디테일은 전부 의심. — 예: 특정 SDK 미디에이션을 "내장(embedded) 지원"으로 적었으나 실제로는 "지원 개발 중"이라는 사실만 확인된 경우, 구현 방식 표현은 전부 제거한다.

## 8.5 동의어 중복 강조 금지 — 같은 뜻 두 번 겹치기

**같은 의미를 가진 두 표현을 나란히 써서 강조하는 것은 AI 말투다.** 사람은 "선행"이 이미 "먼저"라는 뜻인 걸 알기 때문에 굳이 둘 다 쓰지 않는다. AI 는 강조하려고 유의어를 겹쳐 쓰는 경향이 있다 — grep 상투어·수사의문문 패턴으로는 안 걸리고, 문장을 의미 단위로 읽어야 보인다.

| ❌ 동의어 중복 | ✅ 하나만 |
|---|---|
| "선행 단계에서 먼저 잡는다" (선행=먼저 인데 둘 다) | "조기에 잡는다" / "선행 지표 단계에서 포착한다" |
| "다시 한번 재확인한다" (다시=재, 둘 다) | "재확인한다" |
| "완전히 다 끝났다" | "완전히 끝났다" |
| "이미 벌써 지나갔다" | "이미 지나갔다" |
| "각각 따로따로 처리한다" | "각각 처리한다" |

**판별법**: 제목·라벨의 두 수식어를 하나씩 지워보고, 지워도 뜻이 그대로면 중복이다 → 하나만 남긴다. 특히 라벨(볼드 리드 문구)에서 강하게 나타난다 — 본문보다 라벨을 먼저 의심할 것.

## 8.6 대시(—) 전면 금지

**모든 산출물에서 대시(`—`, `–`)를 쓰지 않는다.** 본문의 절 연결은 물론 제목·라벨의 `대주제 — 부제` 구분자도 금지다. 대시는 AI 글쓰기의 가장 눈에 띄는 흔적이고, 문장 중간에 끼면 시선이 끊긴다(실측 피드백: "문장과 문장 사이에 바가 들어가면 필연적으로 가독성이 안 좋아짐", "전반적으로 슬라이드에서 — 기호 뺄 것", "— 랑 · 절대로 쓰지 말라는 내용이 빠짐?").

| 자리 | ❌ 대시 | ✅ 대체 |
|---|---|---|
| 본문 절 연결 | "커넥터 60여 종 기구축 — 물리적으로 시간이 드는 작업" | "커넥터 60여 종이 이미 갖춰져, 시간이 드는 연동 작업을 생략" |
| 본문 절 연결 | "강한 스키마 규약 — 기능 1건에 4곳 수정" | "강한 스키마 규약 탓에 기능 1건에 4곳 수정이 필요" |
| 제목 구분자 | "배경 — 모델 교체마다 반복되는 지시문 재작성" | "배경: 모델 교체마다 반복되는 지시문 재작성" / "모델 교체마다 반복되는 지시문 재작성" |
| 노드 라벨 | "coordinator — Run 소유" | "coordinator(Run 소유)" |
| 기간 | "'26.1—8" | "'26.1~8" |

**대체**: 콜론(`:`), 괄호, 쉼표, 물결(기간), 문장 분리. 영어 원문 인용 안의 대시는 인용 부호 안에서만 유지한다.

## 8.7 사용자 구어 문장 교정 — 요청문을 그대로 싣지 않기

**사용자가 대화로 준 구어 문장("~해달라", "~하면 좋겠다", 반말 지시)을 산출물에 그대로 옮기지 않는다.** 의미만 취하고 어조는 문서 톤(개조식 명사형)으로 교정한다. 사용자의 문장 제안은 *내용* 확정이지 *표기* 확정이 아니다.

| ❌ 구어 그대로 | ✅ 문서 톤 교정 |
|---|---|
| "본부 업무를 PO 중심으로 개편해달라" (제목) | "본부 업무를 Product Owner 중심으로 개편" |
| "~하면 좋겠다" | 해당 내용의 명사형 서술 |

(실측 피드백: 요청 문장을 교정 없이 실었다가 "실장 보고 문장 이게 실화?" 지적.)

## 8.8 알림 문맥 '발화' 금지 — fire 번역투

**알림·경보·판정 조건이 "발화했다"는 표현을 쓰지 않는다.** 영어 fire(알림이 걸리다)의 직역으로, 모니터링·알림 문서에서 AI 가 반복 생성하는 번역투다. 파생형(`발화율 / 발화일 / 재발화 / 밀집 발화 / 발화 전수`)까지 전부 금지. 대체어: `트리거되다 / 활성화되다 / 발생하다`.

| ❌ fire 번역투 | ✅ 대체 |
|---|---|
| "이상 구간 5건을 산식이 전부 발화로 잡았다" | "이상 구간 5건이 전부 해당 산식에서 트리거되었다" |
| "#6~8 이 6/10부터 발화했다" | "#6~8 이 6/10부터 트리거되었다" / "활성화되었다" |
| "발화율 65%" | "트리거율 65%" |
| "시뮬레이션 발화일" | "알림이 트리거된 날" |
| "L1 재발화" | "L1 재트리거" |

(실측 피드백: "발화라는 단어 금지. 전형적인 AI 표현.")

## 8.9 대조 강조 구문 금지 — "남은 것은 A 가 아니라 B 다"

**"X 는 A 가 아니라 B 다" 대조 프레임으로 결론을 강조하지 않는다.** 요점을 극적으로 만들려는 영어 상투구("It's not X, it's Y")의 직역으로, AI 가 결론 문장에 반복 사용한다. 부정 절 없이 사실을 바로 단정한다.

| ❌ 대조 강조 | ✅ 직접 단정 |
|---|---|
| "남은 것은 산식이 아니라 임계 캘리브레이션 2건" | "남은 과제는 임계 캘리브레이션 2건" |
| "중단 '지속' 은 L1 재트리거가 아니라 L2 몫" | "중단 '지속' 감시는 L2 담당이고, L1 은 재트리거하지 않는다" |
| "중요한 것은 속도가 아니라 정확도다" | "정확도가 우선이다" |

**판별법**: "~가 아니라" 절을 지우고 긍정 절만 남겨도 정보 손실이 없으면 강조용 프레임이다 → 긍정 단정만 남긴다. A·B 의 역할 구분 자체가 정보라면 두 절을 각각 단정문으로 쓴다("B 담당이다. A 는 하지 않는다").

(실측 피드백: "남은 것은 ~~가 아니라 ~~다 → 전형적인 AI 표현. 금지할 것.")

## 8.10 계층 코드 라벨 금지 — `L0~L5` 식 단계 표기

**문서가 새로 만든 체계의 단계를 `L0~L5`·`Layer 3`·`T1/T2` 같은 코드로 부르지 않는다.** 독자는 코드를 볼 때마다 정의표로 되돌아가야 하고, 정의표가 없으면 각 단계가 무엇인지 끝까지 모른다. `N단계 이름` 으로 부르고, 첫 등장 전에 단계 정의 표를 둔다(§10.3).

| ❌ 계층 코드 | ✅ 번호 + 이름 |
|---|---|
| "6계층(L0~L5) 디렉터리 구조" | "6단계 디렉터리 구조" + 단계 정의 표 |
| "모델 종속 nudge 는 L4 어댑터 계층에만" | "모델 종속 조정 문구는 4단계 모델 어댑터 파일에만" |
| "L0~L3, L5 는 건드리지 않음" | "4단계 어댑터 외 다섯 단계는 유지" |
| "L3 hook/gate 설계에 영향" | "3단계 hook·gate 설계의 전제" |

**예외**: 업계 표준 용어는 유지한다. OSI L7, CPU L2 캐시, 알림 등급 L1/L2 처럼 독자가 이미 아는 코드다. **판별법**: 이 문서가 처음 정의한 체계인가 → 코드 금지. 기존 용어를 인용한 것인가 → 유지.

**적용 범위**: 본문뿐 아니라 문서가 직접 쓴 디렉터리 트리 주석(`# L4: 어댑터`)·표 헤더·그림 라벨도 바꾼다. 코드 블록이라도 명령어·경로가 아닌 문서 자신의 설명 주석은 교정 대상이다.

(실측 피드백: "단계별 구성을 L0~L5 식으로 표현하는 것 지양 → 1단계 2단계 등")

## 8.11 추상명사 의인화 금지 — "근거가 수렴한다"

**근거·증거·결론·연구 같은 추상명사를 주어로 두고 움직임·발화 동사(수렴하다·모이다·가리키다·향하다·말하다)를 붙이지 않는다.** 영어 "evidence converges / points to" 의 직역이다. 사람은 근거를 나열한다: "근거는 세 가지다", "근거는 X 다".

| ❌ 의인화 | ✅ 나열·단정 |
|---|---|
| "증거가 실무·연구 양쪽에서 수렴한다" | "근거 두 가지: 실무 보고 A, 연구 B" |
| "두 결과가 같은 방향을 가리킨다" | "두 결과 모두 X 다" |
| "데이터가 말해 준다" | "데이터상 X 다" |
| "(커뮤니티·연구 수렴)" | "(커뮤니티·연구 공통)" |
| "이 문서는 고정할 부분과 변경할 부분의 경계, 검증 배치, 회귀 테스트 방법에 답한다" | "**대상: 모델 무관 고정 범위와 모델별 변경 범위의 경계, 검증 역할의 벤더 배치, 하네스 설정 회귀 테스트**" |
| "이 보고서는 ~를 제안한다 / 보여준다 / 다룬다" | 주어 없이 "~를 제안한다" 또는 "제안: ~" |

**문서 자기지칭 의인화**: "이 문서는 ~에 답한다" 는 두 번 틀린다. 문서는 답하지 않고 사람이 답하며, 답은 앞서 던진 질문에만 하는 것이라 묻지 않은 것에 "답한다" 고 쓸 수 없다. 문서가 무엇을 다루는지는 주어 없는 문장이나 `대상: ~` · `범위: ~` 명사구로 쓴다.

**판별법**: 주어를 사람으로 바꿔 읽어 "근거가 걸어간다" 처럼 어색하면 의인화다. 통계·수학의 수렴(급수·최적화·분포)은 유지한다.

(실측 피드백: "~에 답한다라니 누가 답을 하는데? 문서가? 답은 질문에 대해서 하는 것이지 묻지도 않은 것에 대해 답하지 않는다")

(실측 피드백: "사람은 근거를 수렴한다고 표현하지 않는다. 근거는 1 2 3 이다 또는 근거는 무엇이다 라고 말한다")

## 8.12 핵심 문장의 프레임 조어 금지 — 주장을 포장하지 않는다

**핵심 문장(요약 훅·볼드 리드·절 첫 문장)은 주장 자체여야 한다.** "문제는 ~라는 점이다", "이 문서가 답하는 질문은 세 가지다" 처럼 주장을 서술 틀로 감싸면 핵심이 틀 안에 묻힌다. 본문 서술에서는 허용되는 문형이라도 핵심 문장 자리에서는 금지다. 명사구·명사절로 끝내거나, 주어 + 술어의 최소 구성(수식절 1개 이하)으로 쓴다.

네 가지 틀을 벗긴다.

| 틀 | ❌ 포장된 핵심 문장 | ✅ 주장 자체 |
|---|---|---|
| 서술 포장 `X 는 ~는 점이다 / ~는 것이다 / ~기 때문이다` | "문제는 두 벤더의 프롬프팅 가이드가 정반대 방향의 조정을 요구한다는 점이다." | "두 벤더의 프롬프팅 가이드는 정반대 방향의 조정을 요구한다." / "두 벤더 프롬프팅 가이드의 상반된 조정 방향" |
| 자기지칭 예고 `이 문서가 답하는 질문은 N 가지다 / ~은 다음과 같다` | "이 문서가 답하는 질문은 세 가지다." | "모델 교체 문제의 해법 세 가지" (소제목) 뒤에 바로 목록 |
| 개수만 말하는 리드 `~는 N 가지다 / N 갈래다 / N 항목이다 / ~은 셋이다` | "결정을 바꾸는 임계치는 세 가지다." / "새 모델 온보딩 체크리스트는 아홉 항목이다." / "소음의 원천은 셋이다." | "결정을 바꾸는 임계치: 검출률·CI 통과율·정책 코멘트 수" / 리드를 빼고 목록만 / "노이즈의 세 가지 원인" (§10.5) |
| 접속 부사 시작 `따라서 / 종합하면 / 즉 / 결국` | "종합하면 교차 벤더 검증은 고위험 경로에서 가치가 크다." | "교차 벤더 검증의 가치는 고위험 경로에서 크다." |

**판별법**: 틀에 해당하는 어절(`문제는`·`~는 점이다`·`답하는 질문은`·`다음과 같다`·`세 가지다`·`따라서`)을 지웠을 때 남는 부분이 그대로 핵심 문장이 되면 틀이다 → 남는 부분만 쓴다. 지웠더니 내용이 없으면(개수만 말한 리드) 리드 자체를 빼고 목록·소제목으로 대체한다. 볼드가 아닌 평문이라도 목록 바로 앞에서 개수만 말하면 같은 틀이다(§10.5).

**형태 선택 — 명사구가 자연스러우면 명사구, 동작이면 동사 문장. `X 는 Y 다` 복사 구조는 기본 금지.** 핵심 문장이 주어 + 술어일 필요는 없다. 핵심이 사물·구조·개수·대상이면 명사구로 끝내고 부연은 뒤 평문에 둔다. 핵심이 사건·동작·판정이면 실제 동사가 있는 문장으로 쓴다. `X 는 Y 이다 / Y 다` 로 명사를 명사에 잇는 복사 구조와 `~가 명확하다 / 중요하다 / 크다` 같은 내용 없는 형용사 판정은 AI 티가 가장 강하게 나는 문형이므로, 정말 잘 쓴 경우가 아니면 쓰지 않는다.

| 핵심의 종류 | ❌ 복사 구조 리드 | ✅ 형태를 고른 리드 |
|---|---|---|
| 구조·개수 | "워크플로우를 6단계로 나누고 모델 의존은 4단계에만 둔다." | "**워크플로우 6단계.** 모델 의존은 4단계 어댑터 파일에만 둔다." |
| 구성 요소 | "Orca 의 역할 간 계약은 메시지 타입·필수 ID·outcome 세 가지다." | "**역할 간 계약 3요소: 메시지 타입·필수 ID·outcome**" |
| 원인 | "재작성 비용의 원인은 두 벤더 가이드의 상반된 조정 방향이다." | "**재작성 비용의 원인: 두 벤더 가이드의 상반된 조정 방향**" |
| 대상 하나 | "Codex 등가물은 `codex exec` 다." | "**Codex 등가물 `codex exec`**" |
| 내용 없는 판정 | "migrate 스킬이 바꾸는 것과 사람에게 남기는 것의 경계가 명확하다." | "**migrate 스킬의 자동 처리 범위와 수동 잔여 범위**" (뒤에 두 범위를 나열) |
| 동작·사건 | (문장이 맞음) | "**Orca 는 지원 에이전트 전부를 권한 우회 플래그로 미리 채워 실행한다.**" |

**판별법**: 리드의 술어가 `이다 / 명사+다 / 명확하다·중요하다·크다` 이면, 술어를 떼고 `X 의 Y` · `X: Y` 명사구로 바꿔 읽는다. 더 자연스러우면 명사구로 쓴다. 명사구로 바꿨더니 내용이 비면(경계가 명확하다 → "경계") 리드가 판정을 담지 못한 것이므로 실제 내용으로 다시 쓴다. 동사가 살아 있는 문장(실행한다·요구한다·건너뛴다)은 그대로 둔다.

**한 절 원칙 — 핵심 문장에 부연을 싣지 않는다.** 핵심 문장은 절 하나, 40자 안팎이다. 연결 어미(`-이고 / -하고 / -며 / -지만 / -어서 / -므로 / -면서 / -는데`)로 둘째 절을 이어 붙이면 둘째 절은 예외 없이 부연이다. 부연은 다음 줄로 내린다(§11.5).

| ❌ 두 절 리드 | ✅ 한 절 + 부연 |
|---|---|
| "**Orca 오케스트레이션은 experimental 이고 레거시 명령은 deprecated 되어 효과가 없다.**" | "**Orca 오케스트레이션은 experimental 이다.**" ↵ "플래그가 버전마다 바뀌고, 레거시 명령은 deprecated 되어 효과가 없다." |
| "**verifier 는 executor 와 다른 벤더의 워커로 실행하고 병합은 decision gate 뒤에 둔다.**" | "**verifier 는 executor 와 다른 벤더로 둔다.**" ↵ "병합은 decision gate 뒤에 둔다." |

**판별법**: 리드에서 연결 어미를 찾아 그 뒤를 지운다. 남은 앞 절이 핵심이면 뒤 절은 부연이다. 뒤 절이 핵심이면 앞 절을 부연으로 내린다.

(실측 피드백: "핵심 문장에 부연 설명 빼라고 여러 번 말했을 텐데. Orca 오케스트레이션은 불완전하다 / experimental 하다 / 자주 바뀐다, 이런 게 핵심 문장 아닌가? 레거시 명령은 ~ 가 왜 핵심 문장에 포함되어 있지? 부연 설명으로 내리면 되잖아")

(실측 피드백: "핵심 문장에 쓸데없는 조어나 수식이 있어선 곤란해. 차라리 명사구·명사절로 끝나든지 문장 수식을 최소화하든지." / "XX 가 답하는 질문은 XX 가지다 → 사람은 이런 표현을 안 써." / "핵심 문장이 반드시 주어 술어 구조를 따를 필요는 없다. XX 은 XX 이다 같은 문장은 AI slop 티가 팍팍 나는 촌스러운 문장이다. 워크플로우 6단계가 가장 중요한 내용이다. 이걸 강조하면 된다. 나머지는 부연설명하면 된다")

## 8.13 사람 동사 직역 금지 — retired 를 '은퇴' 로 옮기지 않는다

**기술 용어의 영어 동사를 사람에게 쓰는 한국어 동사로 직역하지 않는다.** 명령·기능·API 는 은퇴하지 않고, 프로세스는 죽지 않으며, 종료는 우아하지 않다. 업계에서 굳은 영어 용어는 번역하지 않고 원문 그대로 쓴다(deprecated, graceful shutdown, kill). 한국어로 옮겨야 할 때만 기술 동사를 쓴다. §8.8 의 fire → '발화' 와 같은 계열이다.

| ❌ 직역 | ✅ |
|---|---|
| "레거시 명령이 은퇴했다 / 은퇴한 명령" (retired) | "레거시 command 가 deprecated 되었다" / "폐기되었다" / "지원이 종료되었다" |
| "프로세스를 죽인다" (kill) | "프로세스를 kill 한다" (명령 그대로) / "종료한다" |
| "우아한 종료 / 우아하게 내린다" (graceful) | "graceful shutdown" (원어 유지) / 굳이 옮기면 "정상 종료" |
| "워커가 살아 있다" (alive) | "워커가 실행 중이다" / "응답한다" |
| "기능이 태어났다 / 죽었다" | "기능이 추가되었다 / 제거되었다" |

**판별법**: 그 동사의 주어를 사람으로 바꿔도 뜻이 같으면(은퇴·죽다·우아하다) 직역이다. 영어 용어 자체(retired, graceful shutdown)는 원문 그대로 두면 되고, 따옴표 인용 안에서도 유지한다.

(실측 피드백: "graceful shutdown 은 그 자체로 직역하지 말고 원문 그대로 보여줘도 되는 기술 용어")

## 8.14 비교·대비 문장의 문법 — '더 + 동사' 와 반의어 쌍

**(1) `더` 뒤에 동작 동사를 바로 붙이지 않는다.** "결함을 더 잡는다" 는 비문이다. 영어 "catches more" 의 직역인데, 한국어의 `더` 는 정도 부사라 무엇이 더한지(많이·잘·자주·빨리)를 받아야 한다. 형용사에는 바로 붙는다(더 크다·더 낫다).

| ❌ 더 + 동사 | ✅ 더 + 정도 부사 + 동사 |
|---|---|
| "교차 벤더 검증은 자기 리뷰보다 결함을 더 잡는다" | "교차 벤더 검증은 자기 리뷰보다 결함을 더 많이 잡는다" / "더 잘 잡는다" |
| "리뷰어가 버그를 더 찾는다" | "리뷰어가 버그를 더 많이 찾는다" |
| "비용이 더 든다" | "비용이 더 많이 든다" |

**(2) 대비 구조는 반의어 쌍으로 쓴다.** 두 항을 맞세울 때 한쪽만 한자어·다른 쪽은 구어이거나, 뜻이 대응하지 않는 짝을 쓰면 문장이 어색해진다. 고정 ↔ 변경, 자동 ↔ 수동, 공통 ↔ 개별, 유지 ↔ 교체.

| ❌ 짝이 맞지 않는 대비 | ✅ 반의어 쌍 |
|---|---|
| "고정할 부분과 갈아 끼울 부분" | "고정 범위와 변경 범위" / "유지할 부분과 교체할 부분" |
| "자동으로 되는 것과 사람이 하는 것" | "자동 처리 항목과 수동 처리 항목" |

**판별법**: (1) `더` 다음 어절이 `~는다 / ~ㄴ다 / ~습니다` 로 끝나는 동사이면 사이에 정도 부사를 넣는다. (2) 대비되는 두 항의 품사·격(한자어 명사 ↔ 한자어 명사)이 같은지 본다.

(실측 피드백: "결함을 더 잡는다는 비문이다. 더 잘 잡거나 더 못 잡거나 하는 거지. it is more 로 문장이 끝날 수는 없다" / "고정할 부분과 갈아 끼울 부분이라니 표현이 어색하다. 고정과 대비되는 단어는 변경이다")

(실측 피드백: "레거시 명령이 은퇴했다라는 표현은 사람은 쓰지 않는다. 레거시 command 가 deprecated 되었다가 더 자연스럽다")

## 8.15 가운뎃점(·) 금지 — 나열·연결·구분자 전부

**가운뎃점을 나열 구분자·명사구 연결·라벨 구분자로 쓰지 않는다.** "CLAUDE.md·AGENTS.md·skill 파일" 처럼 명사를 점으로 줄줄이 잇는 것은 AI 산출물의 전형적 흔적이다. 나열은 쉼표, 명사구 꼬리 연결은 쉼표 또는 괄호, 라벨 구분은 콜론으로 쓴다.

| ❌ 가운뎃점 | ✅ 대체 |
|---|---|
| "CLAUDE.md·AGENTS.md·skill 파일 여러 곳" | "CLAUDE.md, AGENTS.md, skill 파일 여러 곳" |
| "역할 간 계약 3요소: 메시지 타입·필수 ID·outcome" | "역할 간 계약 3요소: 메시지 타입, 필수 ID, outcome" |
| "θ 를 넘으면 트리거 · 기본 θ 15%" (§9.1 명사구 꼬리) | "θ 를 넘으면 트리거, 기본 θ 15%" / "θ 를 넘으면 트리거(기본 θ 15%)" |
| "Run·Task·Dispatch 위에" | "Run, Task, Dispatch 위에" |

**예외**: 굳어진 요일 축약(토·일, 월·수·금)과 고유 표기(인명·지명의 외래어 표기)만 유지한다.

(실측 피드백: "— 랑 · 절대로 쓰지 말라는 내용이 혹시 빠짐?")

## 8.16 굳은 외래어 용어의 한자어 직역 금지 — noise 를 '소음' 으로 옮기지 않는다

**업계에서 외래어 그대로 쓰는 기술 용어를 한자어로 직역하지 않는다.** 알림 문맥의 noise 는 '노이즈' 이지 '소음' 이 아니다. 사전상 맞는 번역이라도 동료가 말로 그렇게 부르지 않으면 번역투다. 외래어 표기(노이즈, 코호트, 레거시)나 영어 원문(horizon, payload) 그대로 둔다. 원문 단어에 대응하는 자연스러운 한국어가 따로 있으면(sources of noise → 노이즈의 원인) 그 말을 쓴다. §8.8 의 fire → '발화', §8.13 의 retired → '은퇴' 와 같은 계열이다.

| ❌ 직역 | ✅ |
|---|---|
| "단순 임계 알람은 소음이 된다" / "잡음" (noise) | "노이즈가 된다" |
| "소음의 원천은 셋이다" (sources of noise) | "노이즈의 세 가지 원인" (원인을 말할 때) / "데이터 출처" (data source) / "소스" |
| "LTV 지평" (horizon) | "LTV horizon" / "LTV 기준 기간" |
| "종단점" (endpoint) | "엔드포인트" |
| "처리기 / 청취자 / 되부름" (handler / listener / callback) | "핸들러 / 리스너 / 콜백" |
| "적재물" (payload) | "페이로드" |
| "동질 집단" (cohort) | "코호트" |
| "알람 음소거" (mute) | "알람 mute" / "알람 끄기" |

**판별법**: 그 단어를 동료에게 말할 때 외래어로 발음한다면(노이즈, 코호트, 핸들러) 글에서도 그렇게 쓴다. 한자어가 현장 어휘인 용어(threshold → 임계, baseline → 기준선, spend → 지출, impression → 노출)는 그대로 둔다. 기준은 사전이 아니라 현장에서 쓰는 말이다. '원천' 은 source 의 직역이므로 뜻에 따라 '원인' (cause), '출처' (data source) 로 나눠 쓴다.

(실측 피드백: "소음이라는 직역보다는 노이즈가 자연스럽다. 일부 표현 중에 영어 원문을 그대로 써야 자연스럽게 읽히는 것들이 있는데, 그런 단어들은 직역하지 말고 원문을 그대로 둬야 한다." / "원천보다는 원인 같은 자연스러운 표현을 쓸 수 있도록 유도할 것")

## 9. 줄바꿈 — 한글은 어절(단어) 단위

한글 본문은 단어 중간에서 끊기면 안 된다. 공유 CSS 파일이 다음을 기본으로 둔다:

```css
html { word-break: keep-all; overflow-wrap: break-word; text-wrap: pretty; }
```

- **어절 단위** 줄바꿈(공백에서만 끊김) + 긴 라틴/코드 토큰만 필요 시 분리 + 마지막 줄 고아 단어(orphan) 완화 → 문장 흐름에 가깝게.
- 새 인포그래픽은 공유 CSS 를 상속하므로 **자동 적용**. 자체 `word-break` 재정의 금지.
- 특정 제목/문구를 문장 단위로 딱 끊고 싶으면 의도적 `<br>` 또는 `&nbsp;` 로 어절을 묶는다.

### 9.1 문장 경계 줄바꿈 — 다문장 단락은 문장마다 끊는다

슬라이드·카드·인포그래픽처럼 **폭이 고정된 텍스트 블록**에서 두 문장 이상인 단락을 자동 래핑에 맡기면, 줄바꿈이 문장 중간의 어중간한 어절에서 일어나 가독성이 떨어진다. **문장 경계(마침표 뒤)에 명시적 `<br>` 를 넣어 문장마다 줄을 시작**한다.

**이 규칙은 본문을 쓰는 시점에 적용한다. 마무리 점검으로 미루지 않는다.** 어휘 grep 으로 잡히지 않는 구조 규칙이라, 다 쓴 뒤 점검에 기대면 새로 쓴 문단에서 반복 누락된다(실측: grep 통과를 마무리 기준으로 삼은 산출물에서 새 문단 13곳 누락). `<p>`·`<dd>`·`<li>`·카드 설명 문자열에 둘째 문장을 쓰는 순간 앞 마침표 뒤에 `<br>` 를 넣는다. 마무리의 「§9.1 구조 검출기」는 누락분을 잡는 보조 수단이다.

❌ 자동 래핑에 맡김 (둘째 문장이 중간에 꺾임):

```
개발팀장급에게 제공되는 본부 내 정보가 제한적. 주요 사업 정보와 의사결정 사항이 기술
조직에 전달되지 않음.
```

✅ 문장 경계에서 끊음:

```
개발팀장급에게 제공되는 본부 내 정보가 제한적.
주요 사업 정보와 의사결정 사항이 기술 조직에 전달되지 않음.
```

- 적용 대상: 카드 설명문·정의 패널·하이라이트 바·부제 등 **여러 문장이 든 좁은 블록 전부**. HTML 로는 `<p>`·`<dd>`·`<li>`·`<small>` 본문과 `innerHTML` 로 주입되는 JS 문자열(`desc`·`read`·`doc` 류 키의 값). 한 문장이 한 줄을 넘겨 내부에서 래핑되는 것은 허용(어절 단위 규칙이 처리).
- MD 산출물은 렌더러가 단일 개행을 접으므로 `<br>` 대신 §11.2 문단 분할(빈 줄)로 대응한다. §9.1 은 HTML 산출물에서 적용.

**고아 조각 예외: 명사구 꼬리는 `<br>` 대신 쉼표로 잇는다.** 문장 경계 `<br>` 는 뒤 조각이 완결 문장일 때만 넣는다. 뒤 조각이 스펙 값, 단위, 짧은 라벨 같은 명사구 꼬리이면 `<br>` 로 끊었을 때 그 조각이 단독 줄(고아 조각)로 남는다. 고아 조각 단독 줄은 금지이므로, 이때는 줄을 끊지 않고 문장 경계 자체를 없앤다: 마침표를 쉼표 연결(`, `) 또는 괄호로 바꾼다. 가운뎃점(` · `)은 쓰지 않는다(§8.15).

| 뒤 조각 | 처리 | 예 |
|---|---|---|
| 완결 문장(술어 있음) | 마침표 뒤 `<br>` | `…정보가 제한적.<br>주요 사업 정보가 전달되지 않음.` |
| 명사구 꼬리(스펙 값, 단위, 라벨) | 마침표 → `, ` 또는 괄호 | `…알림 트리거. 기본 θ 15%` → `…알림 트리거, 기본 θ 15%` |

## 10. 문단·구조 — 2b단계 (맥락 교정)

문장 단위가 깨끗해도 구조가 AI스러우면 독자는 "그래서 뭘 하라는 건지" 를 모른다. 이 절은 문서 전체의 뼈대 규칙이다. 패턴 grep 으로 잡히지 않으므로 문서를 처음부터 끝까지 읽고 판단한다.

### 10.1 요약 = 핵심 문장 + 짧은 뒷받침

**요약(TL;DR·요약·Summary)은 본문의 압축본이 아니라 독자가 본문을 읽을지 결정하게 하는 훅이다.** 본문에서 다룰 내용을 요약에 다시 채우지 않는다.

- 항목 3~5개. 각 항목은 **볼드 핵심 문장 1개(60자 이내, 판정이 담긴 완결 문장)** + 뒷받침 1~2문장(항목 전체 200자 이내). 핵심 문장은 §8.12 프레임 없이 주장 자체로 쓴다.
- 출처 URL·명령어·옵션 나열·수치 열거는 본문으로 보낸다.
- 요약 문장이 본문에 그대로 다시 나오면 요약이 아니라 중복이다.

| ❌ 압축본 요약 | ✅ 훅 + 뒷받침 |
|---|---|
| "**모델별 지시문을 계속 다시 쓰는 문제는 "6계층 분리 + 모델 어댑터 계층 격리"로 구조적으로 해결할 수 있다.** 벤더 문서가 이를 직접 뒷받침한다: Anthropic 은 `/claude-api migrate`, OpenAI 는 `$openai-docs migrate` 로 모델 종속적 변경을 자동화하고, 두 벤더 모두 "설정 파일(CLAUDE.md/AGENTS.md/skills)을 감사하라"고 명시한다. 즉 워크플로우 구조(L0~L3, L5)는 …" (282자) | "**모델이 바뀔 때 고칠 파일을 하나로 줄인다.** 워크플로우를 6단계로 나누고 모델 종속 문구는 4단계 어댑터 파일에만 둔다. 두 벤더의 migrate 스킬이 그 파일을 재생성한다." |

**판별법**: 요약 항목에서 볼드를 뺀 나머지를 지워도 독자가 결론을 아는가 → 볼드가 훅이다. 볼드만 읽어서 결론을 모르면 훅이 아니라 주제 라벨이다.

(실측 피드백: "요약은 매우 가독성이 좋은 & hook 이 있는 핵심 문장 몇 가지와 그 문장을 뒷받침하는 짧은 설명으로 충분하다. 본문에서 다룰 것이기 때문이다")

### 10.2 문제제기 절 — 왜 이 글인가

**본문 첫 절은 이 문서가 존재하는 이유를 서술한다.** 순서는 현재 상태 → 무엇이 문제인가(비용·반복·위험) → 이 문서가 답하는 질문. 절 이름은 개요·배경·문제·동기 무엇이든 된다. 요약에 "문제는 ~로 해결할 수 있다" 가 있어도 문제 자체의 서술은 아니다.

| ❌ 동기 없이 발견으로 직행 | ✅ 문제제기 절 |
|---|---|
| "## 요약 … ## 핵심 발견 1. Orca 오케스트레이션은 experimental 이며 …" | "## 배경: 모델이 바뀔 때마다 지시문을 다시 쓴다<br>현재 CLAUDE.md·AGENTS.md·skill 파일 여러 곳에 모델별 조정 문구가 흩어져 있다. 새 모델이 나올 때마다 전부 다시 쓴다.<br>이 문서는 무엇을 모델 무관하게 고정하고 무엇만 갈아 끼울지 답한다." |

**판별법**: 문서 어디에도 "지금 무엇이 문제라서" 가 없으면 위반. 검출기(`check_md_layout.py`)는 절 제목 이름으로만 추정하므로, 다른 이름의 절에 동기가 있으면 통과로 판정하고 보고에 남긴다.

(실측 피드백: "무엇이 문제여서 이런 개선을 하려는 건지가 드러나지 않는다. 명시적으로 단락명이 문제제기일 필요는 없으며 개요여도 된다")

### 10.3 단계 체계는 정의가 먼저 — "그래서 뭘 해야 하는가"

**문서가 단계·계층·층위 체계를 도입하면 처음 쓰기 전에 정의 표를 둔다.** 열은 `단계 | 이름 | 하는 일(동사) | 산출물·파일`. 이후 본문은 `N단계 이름` 으로 지칭한다(§8.10). 행동 지시 절(권장 조치·체크리스트)의 각 항목은 대상·동사·산출물 세 요소를 갖는다.

| ❌ 정의 없는 코드 참조 | ✅ 정의 표 선행 |
|---|---|
| 디렉터리 트리 주석에만 `# L0`, `# L4` 가 있고 본문은 "L4 어댑터만 갱신" | 표: `4단계 \| 모델 어댑터 \| 모델별 조정 문구를 한 파일에 모은다 \| .claude/adapters/<model>.md` → 본문 "4단계 어댑터 파일만 갱신" |
| "skill 감사: 두 벤더 모두 명시 권고" | "skill 파일을 감사한다. 레시피식 라인을 지우고 최소 라우터로 줄인다. 산출물은 줄어든 SKILL.md" |

**판별법**: 독자가 "N단계" 를 처음 만났을 때 그 위쪽에 정의가 있는가. 없으면 위반.

(실측 피드백: "0단계~5단계가 각각 무엇을 의미하는지에 대한 서술이 전혀 없다. 각 단계별로 무엇을 해야 하는지도 가독성이 떨어진다")

### 10.4 절 첫 문장 = 결론

**절·소절의 첫 문장은 그 절의 판정이다.** 배경·인용·정의는 그 뒤에 온다. 독자가 각 절의 첫 문장만 이어 읽어도 논지가 되어야 한다.

| ❌ 배경으로 시작 | ✅ 판정으로 시작 |
|---|---|
| "Orca 는 ADE 로, 25개 이상의 CLI 에이전트를 … 병렬 실행한다. 공식 사이트는 … 로 소개한다. Orca 는 Stably AI 의 …" | "**Orca 의 역할 간 계약은 메시지 타입·필수 ID·outcome 세 가지다.** Orca 는 CLI 에이전트 25종을 격리 worktree 에서 병렬 실행하는 ADE 다. …" |

**판별법**: 각 절 첫 문장만 모아 읽어 흐름이 되면 통과.

### 10.5 목록 도입부는 명사구 — "원인은 셋이다" 로 목록을 열지 않는다

**목록 바로 앞의 도입 문장은 명사구로 쓴다.** "소음의 원천은 셋이다." 처럼 개수만 말하는 문장으로 목록을 여는 것은 §8.12 개수만 말하기 틀의 평문판이다. 볼드가 아니어도 같은 AI 문형이다. 목록이 개수를 이미 보여 주므로 "노이즈의 원인" 으로 충분하고, 개수를 짚어 주려면 "노이즈의 세 가지 원인" 처럼 수사를 명사구 안에 넣는다.

| ❌ 개수 예고 문장 + 목록 | ✅ 명사구 도입 + 목록 |
|---|---|
| "소음의 원천은 셋이다." | "노이즈의 세 가지 원인" / "노이즈의 원인" |
| "선택지는 두 가지다." | "두 가지 선택지" / "선택지: A 또는 B" |
| "확인할 항목은 다음과 같다." | "확인 항목" (소제목) 뒤에 바로 목록 |
| "백테스트 대상은 4개다." (목록 없는 사실 서술) | 유지. 목록 도입이 아니면 대상이 아니다 |

**판별법**: 목록 바로 위 문장의 술어가 `N 이다 / N 가지다 / N 개다 / 다음과 같다` 이면 주어부를 명사구로 바꾸고 수사를 그 안에 넣는다. 목록 없이 사실 수치를 말하는 문장은 대상이 아니다. 검출기(`check_md_layout.py`)는 목록 직전 문단이 이 술어로 끝나면 위반으로 센다.

(실측 피드백: "소음의 원천은 셋이다 → XX은 [숫자]이다 패턴이 전형적인 AI스러운 문구인데 여전히 검출이 안 되네?" / "불릿포인트로 항목 나열할 때는 노이즈의 원인 정도로도 충분하다. 몇 가지인지 짚어주려면 Noise 의 세 가지 원인처럼 문장 구조를 개선할 것")

## 11. 가독성 — 3단계 (키프레임·문단·강조, 모든 산출물)

### 11.1 키프레임 — 훑어읽기 테스트

**글은 훑어 읽힌다. 제목·볼드 리드·표 헤더·목록 첫 어절만 읽어도 문제→원인→해결→행동의 흐름이 재구성되어야 한다.** 화면 한 장(약 900자)마다 시선 고정점이 하나 이상 있어야 한다: 소제목, 볼드 판정 문장, 표, 목록, 코드 블록.

두 종류의 키프레임을 구분한다.

| 자리 | 형태 | 답하는 질문 |
|---|---|---|
| 제목·부제·표 헤더 | 명사구(§8) | 무엇에 관한 절인가 |
| 문단 볼드 리드 | 판정이 담긴 완결 문장 | 그래서 무엇이 어떻다는 것인가 |

볼드 리드가 라벨이면 키프레임이 아니다. 리드가 "문제는 ~는 점이다"·"~는 세 가지다" 같은 틀에 싸여 있으면 §8.12 로 벗긴다.

| ❌ 라벨 리드 | ✅ 판정 리드 |
|---|---|
| "**Orca (onorca.dev)** — Orca 는 ADE 로 …" | "**Orca 는 CLI 에이전트 25종을 격리 worktree 에서 병렬 실행한다.**" |
| "**안정적 계약(stable contract):** 워커 완료·heartbeat 메시지는 …" | "**역할 간 계약은 메시지 타입·필수 ID·outcome 세 가지다.**" |
| "**비대화형 실행 메커니즘 (Claude Code):**" | "**`claude -p` 는 CLAUDE.md·skills·hooks 를 건너뛰므로 eval 은 명시 로드로 돌린다.**" |

(실측 피드백: "중요한 제목·핵심 문장 등이 제대로 강조되지 않음. 마치 영상의 키프레임처럼 글의 흐름을 파악할 수 있는 핵심 문장이나 단어, 구조가 있어야 함")

### 11.2 문단 분할 — 한 문단 한 생각

**문단(목록 항목 포함)은 3문장·260자 이내.** 넘으면 문장 경계에서 빈 줄로 나눈다. 목록 항목이 3문장을 넘으면 소제목 + 문단으로 승격한다. 표 셀은 2문장 이내.

- MD: 단일 개행은 렌더러가 접으므로 **반드시 빈 줄**로 나눈다.
- HTML 고정폭 블록: §9.1 문장 경계 `<br>`, 명사구 꼬리는 쉼표.
- 슬라이드, 카드: 한 블록 한 문장이 기본.

| ❌ 한 문단 7문장 330자 | ✅ 세 문단 |
|---|---|

### 11.3 강조 배분

**문단당 볼드는 리드 1개가 기본, 최대 2개.** 셋 이상이면 강조가 사라진다. 볼드는 판정 문장에만 쓰고 고유명사·라벨에는 쓰지 않는다. 볼드가 하나도 없는 900자 이상의 절은 §11.1 위반이다.

### 11.4 목록·표 형식

- 병렬 항목은 목록. 항목마다 첫 어절을 대상(명사) 또는 동사로 통일한다.
- 번호 목록은 순서가 있을 때만. 순서가 없으면 글머리표.
- 표는 비교축이 2개 이상일 때. 항목 나열은 목록.
- 목록 항목 안에 또 다른 절차를 문장으로 늘어놓지 않는다. 절차는 번호 목록으로 승격.

### 11.5 핵심 문장 뒤 줄바꿈 — 핵심 · 줄바꿈 · 부연

**볼드 핵심 문장과 부연을 같은 줄에 잇지 않는다.** 순서는 핵심 문장 → 줄바꿈 → 부연 서술이다. 핵심 문장이 단독 줄에 서야 훑어 읽을 때 눈에 걸린다(§11.1 키프레임).

MD 는 단일 개행을 접으므로 다음 형식을 쓴다.

```markdown
**핵심 문장.**

부연 문장. 부연 문장.

- **목록 항목의 핵심 문장.**

  부연 문장(공백 2칸 들여쓰기, 앞에 빈 줄).

1. **번호 항목의 핵심 문장.**

   부연 문장(공백 3칸 들여쓰기).
```

목록 항목에서는 리드 줄 끝에 공백 두 칸(hard break)을 두고 다음 줄에 부연을 써도 된다. HTML 은 리드 뒤 `<br>` 또는 리드를 별도 요소(`<strong>` 블록·`<dt>`)로 둔다.

| ❌ 같은 줄 | ✅ 줄바꿈 |
|---|---|
| "**모델이 바뀔 때 고칠 파일을 하나로 줄인다.** 워크플로우를 6단계로 나누고 …" | "**모델이 바뀔 때 고칠 파일을 하나로 줄인다.**" ↵ (빈 줄) ↵ "워크플로우를 6단계로 나누고 …" |

**예외**: `**라벨**: 설명` · `**라벨**(§8.4): 설명` 처럼 볼드가 문장이 아니라 라벨(마침표 없음, 바로 뒤에 `:` 나 괄호)인 목록은 같은 줄을 허용한다. 요약(§10.1)의 훅 문장에도 이 규칙이 적용된다.

(실측 피드백: "굵은 글씨의 핵심 문장 이후 부연 서술 내용이 줄바꿈이 되었더라면 더 가독성이 높아졌을 것이다. 핵심 문장 - 줄바꿈 - 부연 서술")

## 점검 스크립트 — 단계별 결정론적 관문

패턴 목록과 검출 논리는 `scripts/` 가 원본이다. 규칙을 추가할 때는 이 문서의 절과 스크립트의 규칙 표를 함께 고친다.

| 단계 | 스크립트 | 대상 | 통과 기준 |
|---|---|---|---|
| 1단계 어휘·패턴 | `python3 scripts/check_lexical.py [--honorific] <file>...` | MD·HTML 전부 | `hits: 0`. 수동 확인 표시 규칙은 예외 판단 후 사유를 보고에 기록 |
| 3단계 MD 구조·가독성 | `python3 scripts/check_md_layout.py <file.md>...` | MD | `violations: 0` |
| 3단계 HTML 줄바꿈 | `python3 scripts/check_br.py <file.html>...` | HTML | `violations: 0` |

**check_lexical.py** — §2·§3·§4·§5·§8~§8.16 의 어휘 신호 27종을 정규식으로 잡는다. §8.12 개수 예고 문장(`~은 셋이다 / ~는 세 가지다`)과 §8.16 외래어 직역(`소음·원천·지평·종단점·처리기`)은 수동 확인 규칙이다(사실 수치, 물리적 소음, 원천징수 같은 본뜻이면 유지). `--honorific` 은 §6 존대 문서에서만 켠다(평어체 잔존 검출). 규칙 표는 파일 상단 `RULES` 리스트. 임시 확인은 `grep -nE "<패턴>" <file>` 로도 된다.

**check_md_layout.py** — §8.12 볼드 리드의 프레임 틀(서술 포장·자기지칭 예고·개수만 말하기·접속 부사 시작)과 두 절 리드, §11.5 리드 뒤 같은 줄 부연, §10.1 요약 항목(볼드 훅 유무·60자·3문장·200자), §10.2 문제제기 절 유무(제목 이름 추정, 수동 확인), §10.3 `N단계` 정의 줄 유무, §10.5 목록 직전 개수 예고 문장(`~은 셋이다 / 다음과 같다`), §11.1 키프레임 공백(900자), §11.2 문단 길이(3문장·260자), §11.3 볼드 남발(3개 이상). 코드 블록·표·HTML 블록은 제외.

**check_br.py**: §9.1 문장 경계 `<br>` 누락. `<p>`·`<dd>`·`<li>`·`<small>` 본문과 인라인 `<script>` 문자열을 `<br>` 로 나눈 세그먼트마다 "문장 종결 마침표 뒤 텍스트" 를 찾는다. 위반 처리는 뒤 조각이 완결 문장이면 `<br>`, 명사구 꼬리면 쉼표. 알려진 오탐은 `e.g.`·`vs.` 약어이며 좁은 블록에서는 `예:`·`대` 로 바꿔 쓴다.

**2a·2b 단계는 스크립트가 없다.** §8.4 미확정 단정·§8.5 동의어 중복·§10.4 절 첫 문장·§11.1 라벨 리드 판정은 문서를 읽고 판단한다. 스크립트 0건은 필요조건이지 충분조건이 아니다.
